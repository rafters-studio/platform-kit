# platform-kit

## 0.2.0

Minor bump: 0.1.1's shipped SQL migrations and their install command are replaced by migratr migrations (#49), which is a breaking change before 1.0. Every platform-auth feature merged since 0.1.1 is in this release.

### Upgrading from 0.1.1

A brand drops the 0.1.1 SQL files (`0001` to `0006` under its wrangler migrations directory) and installs the migratr migrations instead: run `platform-auth-migrations <brand config .json> <migratr migrations dir>`, which copies the needs its config turns on. migratr migrates a local database; smugglr carries the change to D1. Update the three packages to 0.2.0 together.

### Changes

- `@rafters/platform-auth`: native apps sign in with expo and bearer tokens. A brand's `apps` list adds better-auth's bearer plugin for desktop and command-line apps, and a phone app's scheme becomes a trusted origin, with the expo plugin passed in through `AuthDeps`. (#21)
- `@rafters/platform-auth`: recovery by email or backup email, never identity documents. With `recovery.backupEmail` on, a user adds a backup address, verifies it with a verification-code message, and can remove it; only a verified address receives a recovery code, and signing in with that code starts a session on which the user registers a new passkey. (#17)
- `@rafters/platform-auth`: organizations per brand, visible only to their members. The organization plugin joins `authOptions` and `clientPlugins`; `sendInvitationEmail` builds an invitation `SenderRequest` parsed by the contract, and the invitation message accepts only an https url and no control characters in `organizationName` or `role`. (#10)
- `@rafters/platform-auth`: database roles, a permission vocabulary, and the staff organization. Organization roles are rows per organization through dynamic access control, read from the database on every permission check. `/shared` exports the access statements built from the brand's permissions and the default role definitions, `seedStaffOrganization` creates the brand's staff organization with the seven default staff roles once, and a hook refuses a role that grants an action or resource outside the vocabulary. Teams follow `plugins.teams`. (#11)
- `@rafters/platform-auth`: app passwords for apps that only take a username and password. The api-key plugin runs with `enableSessionForAPIKeys` off; a key is a user key named by the user, hashed at rest, carrying the `imap` permission by default. `auth.api.verifyAppPassword` is server only, never over HTTP. (#12)
- `@rafters/platform-auth`: phone number recovery where a brand offers it. `recovery.phone` adds better-auth's phone-number plugin and its client plugin; each text goes to the brand's sender as a `SenderRequest` on channel sms, and sign-up never asks for a number. (#18)
- `@rafters/platform-auth`: vouching recovery, behind `plugins.vouch`. The starting device holds an HTTP-only secret and shows a request code; members of a shared organization approve by code, once each; the device alone registers a passkey after the required approvals and the waiting period. Approvers get no session or token, and completing consumes the request. (#19)
- The brand is bandz, domain bandz.app. Docs, doc comments, and test fixtures use its current name. No change to the published behavior. (#51)
- `@rafters/platform-auth`: vouching keeps the fresh-session rule for signed-in passkey registration. With vouching on, a before hook on the two passkey registration paths refuses a request that carries a stale session, as with vouching off. (#53)
- `@rafters/platform-auth`: identities never cross brands. Two `authOptions` instances with separate databases and secrets: a session or app password from one brand is refused at the other, and the same email at two brands is two user ids. Proven by a two-brand harness and Gherkin scenarios; the harness exports the `Cookie` type. (#14)
- `@rafters/platform-auth`: every recovery is announced on all channels and ends other sessions. A recovery by primary email code (when the user has a passkey), backup email, phone, or vouch signs out the user's other sessions and sends a recovery notice to the primary email, the verified backup email, and the phone. (#20)
- `@rafters/platform-auth`: identity changes are audited through ledger when a brand turns it on. With `ledger: true` the ledger plugin audits user, account, passkey, apikey, session, organization, member, and invitation, each change written with its audit row in one write. The `ledger_audit` migration installs only with ledger on, and `@rafters/ledger` moves to 0.5.0; with ledger off nothing in auth imports it. (#15)
- `@rafters/platform-auth`: deleting a user removes their app passwords again. `referenceId` now holds a user or an organization id, so no database constraint can cascade; a hook deletes a user's app passwords with the user, and organization credentials stay when a user is deleted. (#62)
- `@rafters/platform-auth`: identity changes and failed sign-ins are announced as events, through the `event_relay` migration. Failed sign-in events cover the passkey path as well. (#16)
- `@rafters/platform-auth`: account deletion that meets the brand's regulations and is announced. Last owners are refused, app passwords are revoked, a soft-deleted user cannot sign in, and gdpr erases personal fields from the user row and the audit trail. (#22)
- `@rafters/platform-auth`: organization credentials, for services acting on an organization's behalf. They are keys from the same api-key plugin as app passwords under a second configuration (`organization`), owned by the organization, so they keep working when the member who made one leaves. `POST /organization-credential/create` takes an organization id, a name, and permissions from the brand's vocabulary (anything outside it is refused); listing and revoking are the api-key plugin's `/api-key/list?organizationId=` and `/api-key/delete`. Who may create, list, and revoke is the new `apiKey` role permission (`create`, `read`, `update`, `delete`), held by owner and admin. `auth.api.verifyOrganizationCredential` is the server-only service-side check: it returns the organization, and refuses a credential that is unknown, revoked, deleted with its organization, or missing a required permission. The `org_credentials` migration rebuilds `apikey` without its foreign key to `user`, because a key's owner is now a user or an organization; keys already in the table are dropped with it. (#13)
- `@rafters/platform-auth` ships its schema as one migratr migration per need, replacing the hand-numbered SQL: `migrations/<YYYYMMDDHHMMSS>_<need>.json` for `auth_core`, `passkey`, `organization` and `organization_role` (always installed), `teams` (with `plugins.teams`), `backup_email` (with `recovery.backupEmail`) and `ledger_user_fields` (with `ledger`). `platform-auth-migrations <brand config .json> <migratr migrations dir>` copies the enabled needs' files under their shipped names, copies nothing on a second run, and copies a need turned on later on the next run; migratr applies it. `authOptions` and `clientPlugins` declare the backup address fields only with `recovery.backupEmail` on, so the options and the installed migrations describe the same schema. Tests build every database with the real migratr CLI (`MIGRATR` or `migratr` on PATH), pinned in CI. Carrying the schema to D1 is smugglr's step. (#49)
- Docs: installing migratr for tests, and naming a migration with `migratr new`. (#54)
- Tests: Gherkin scenarios from legion requirements, run by Cucumber.js in strict mode, with `scripts/features.mjs` writing a requirement's scenarios as a feature file and a CI step after `vp test`. (#55)
- Tests: a migration's version is the time its file was added, checked against the commit that added it. (#67)
- Tests: a two-brand isolation suite in CI that counts cross-brand successes and requires zero. (#24)

## 0.1.1

- `@rafters/platform-auth`: social sign-in providers chosen per brand. A brand lists better-auth provider ids in `socialProviders`, and `authOptions` enables exactly those, reading each provider's client id and secret from the env; nothing is enabled by default, a provider the brand did not list is refused, and an unknown id or a missing credential fails at startup, naming it. (#7)
- `@rafters/platform-auth`: tests that the user id is the brand's one identity: a signed-in request reads it as a UUIDv7, it holds across devices, sign-ins, and sign-in methods, and a deleted user's id is never given to another user, with ledger off and on. No change to the published code. (#8)

## 0.1.0

The first release, published by hand from main after #9. Three packages released together at one version: `@rafters/platform-contracts`, `@rafters/platform-sender`, and `@rafters/platform-auth` (subpaths `./shared`, `./server`, `./client`). CI runs on every pull request and merge-queue entry, and a pushed `v*` tag publishes through npm trusted publishing.

- `@rafters/platform-auth`: tests that auth holds no billing data and depends on no payment processor: the shipped schema has no payment, subscription, or processor table or column, with ledger off and on, and neither the package nor its lockfile pulls in a processor SDK. No change to the published code. (#23)
- `@rafters/platform-auth`: one identity across a brand's root domain and its subdomains, from `rootDomain` alone. The session cookie is set on the root domain, the passkey relying party is the root domain, one deployment answers on the root and every subdomain (`baseURL.allowedHosts`), and those origins are trusted. The origin check is set on explicitly, so a page on another site is refused in tests as in production (better-auth turns it off under a test runner otherwise). (#9)
- `@rafters/platform-sender`: adapters behind the contracts `Sender`. `stdoutSender(write?)` is the base adapter: it needs no binding, parses the request, accepts email and sms, and writes one string (recipient line, subject line, blank line, the text body) through `console.log` by default. `emailSender` moves to `adapters/send-email.ts` unchanged. `"."` exports both plus `render`; `./stdout` and `./send-email` export one adapter each. A shared `senderContract` test runs against both. Auth is unchanged: `SENDER` stays required. (#34)
- `@rafters/platform-auth`: every brand gets passkey and email one-time code sign-in. `AuthEnv` takes a `SENDER`; the email code callback builds one `SenderRequest` (the brand's id and sending address, the recipient, a `sign-in-code` with its expiry), checks it against `@rafters/platform-contracts`, and hands it to the sender, which decides delivery. `migrations/0003_passkey.sql` adds the passkey table. (#6)
- `@rafters/platform-sender`: `emailSender(binding)` implements the contracts `Sender` with Cloudflare's `send_email` binding. Each of the five message kinds has a subject, a plain-text body, and a simple HTML body written as template literals, with every request value HTML-escaped. It parses the request with `senderRequest` first, rejects an sms recipient by naming the channel, and lets a binding error reach the caller. (#28)
- `@rafters/platform-auth` ships its schema as SQL: `migrations/0001_auth-core.sql` (better-auth's user, session, account and verification tables) and `migrations/0002_ledger-user-fields.sql` (`deletedAt` and `deletedBy` for a ledger-on brand). `platform-auth-migrations <wrangler migrations dir> [--ledger]` copies the ones the brand does not have yet, numbered after its last migration, and copies nothing when it is up to date; wrangler applies them. A test fails if the SQL and the options `authOptions` returns drift apart. (#5)
- `@rafters/platform-auth`: `authOptions(brand, env)` from `/server` returns better-auth options built from a brand config, validated by `@rafters/platform-contracts` before anything is built, with UUIDv7 ids. `clientPlugins(brand)` from `/client` returns the matching client plugins. With `ledger: true`, the brand passes the ledger module as a third argument and the options add ledger's plugin with user soft delete; a brand with ledger off never loads `@rafters/ledger`, an optional peer dependency. (#4)
- `@rafters/platform-contracts`: the shared Zod schemas every platform package agrees on. A sender request (email or text recipient, one of five message kinds with its own data) and the `Sender` interface; the thin event envelope (UUIDv7 id, brand, subject, time; change events name the record and changed fields, never values; sign-in-failed events carry a subject or a hashed address); and the brand config with every default filled, validated by `parseBrandConfig`, which names every failing path. (#27)
